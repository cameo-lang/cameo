# The IR, and pausing a run at any instruction

This is the plan for an intermediate representation (IR) of cameo programs
that protobuf carries, and for an evaluator that runs it without keeping a
run's state on the Go stack. With both, a run pauses at any instruction, and
its dump holds everything the run was: its code, its classes, its procs and
its call stacks. Nothing here is built yet; *The stack of pull requests*
lists the steps, and each step updates this document to what it built.

## What stops a run from being serialised today

[pause.md](pause.md) describes what a dump holds now. Four things keep the
rest out:

- **Code is Go memory.** A method body is a `*syntax.Def` and a block a
  `*syntax.Block`. Nothing writes an AST node to a message, so a Proc cannot
  travel and a class comes back only by running its definition again.
- **A frame is pointers.** `eval.Frame` points at its method, its classes,
  the instance `initialize` is filling and the block it was given, and a
  `return` finds its frame by pointer identity.
- **Builtins hold Go functions.** A Proc a builtin makes (`Proc.Go`) and an
  Enumerator (`Enumerator.Each`) are Go closures.
- **A running statement is on the Go stack.** The evaluator recurses, and a
  builtin that calls a block (`map`, `each`, `times`) puts a Go frame between
  the method that called it and the block. A run can therefore pause only
  between two top-level statements.

A binding is not among them: `eval.Env` is a table of names and values, and a
block copies the values it sees when it is made
([cameo.md](cameo.md#blocks-capture-values)), so a Proc's binding is a flat
copy that the envelope can carry.

## Decisions

| Topic | Decision | Reason |
|---|---|---|
| Pause points | A run pauses at any instruction. | A script that waits on a host, or loops in one statement, must be persistable where it is. |
| Evaluator | The closure compiler goes first; the tree walker is the one evaluator until the IR replaces it. | One evaluator is ported to the IR, not two. The IR evaluator is where speed is won back. |
| IR shape | Structured stack code: a flat list of instructions per proc, operands on a value stack, control flow as instructions that carry nested lists. No jumps. | A position in the code is a path of indices, which a message carries. The listing reads as assembler. |
| IR level | One instruction per language form, about 45 for about 60 kinds of AST node. | Lowering patterns, rescue and definitions to a small core makes the compiler larger and buys nothing yet. |
| Code in a Proc | By reference: a closure names its unit by digest and its proc by index, and holds its binding. A message carries each unit once. | A thousand procs made by one block carry the code once. This is how an Erlang fun travels: module, index and uniq, with its free variables. |
| Go form | `.proto` files checked in, Go code generated by `protoc-gen-go` and checked in, for the IR, the dump and `cameo.Value`. | One definition of each message. The hand-built descriptors of `protogen/envelope.go` and `protogen/dump.go` go. |
| Tooling | `make proto` regenerates with pinned versions of `protoc` and `protoc-gen-go`; CI fails when the committed files differ. `make build` still needs Go alone. | A contributor who does not touch a `.proto` installs nothing. |
| Dump compatibility | A build resumes a dump of the same IR version. | The dump carries the code it runs, so only the instruction set and the builtins it calls must match. |
| Procs | A Proc crosses `async`, travels to a Go host, is a field of a message, and travels as a Hash's default. | Each restriction existed because a Proc could not be serialised. |
| Classes | The dump carries classes, modules, constants and methods. Resume runs no definition again. | A pause inside a class body, and a method a condition defined, cannot be had by running definitions again. |
| Builtins that call blocks | Resumable step functions in Go: the state between two calls of the block is a cameo value. | No Go frame is live while a block runs, so the stack is all cameo frames. A cameo block cannot accumulate into an outer variable, so these builtins cannot be written in cameo. |
| Enumerators | Step functions too. | An external enumerator's position survives a pause. |
| Host promises | A promise the host has not settled is pending in the dump; the host settles it after resume. `cameo resume`, which has no host, fails it with an exception a script can rescue. | I/O in flight cannot be dumped, and waiting for it makes a pause as slow as the slowest request. |
| Library state | A library may register how the Go state it keeps for a run (`Context.State`) is saved and restored. State without that is lost, and the pause names it. | Most libraries keep none. |

## The IR

A **unit** is the code of one source file: the script, or a library written in
cameo. It holds a table of names and a list of **procs**. A proc is one body:
the top level, a method, a block, a lambda, a class body. An instruction has
an operation, arguments, flags, and for control flow nested instruction
lists. The messages and the operations, each with what it pops and pushes,
are in [src/cameopb/cameo/ir.proto](../../src/cameopb/cameo/ir.proto);
`ir.Listing` prints a unit:

```ruby
def double_all(list) = list.map { |x| x * 2 }
```

```
proc #0 <main>
  DEF double_all #1

proc #1 double_all(list)
  LOAD list
  SEND map 0 #2 block

proc #2 block(x)
  LOAD x
  CONST 2
  SEND * 1 operator
```

`SEND map 0 #2 block` calls `map` with no arguments and the literal block
proc #2: the call makes the closure, a copy of the locals in sight. A
statement ends in `DROP`, which discards its value, so the instruction
after a `DROP` starts a statement; that is where the debugger stops.

```proto
message Unit   { uint32 version = 1; string digest = 2; string file = 3; repeated string names = 4; repeated Proc procs = 5; }
message Proc   { string name = 1; Params params = 2; repeated Code code = 3; int32 line = 4; bool shared = 5; }
message Code   { Op op = 1; repeated Arg args = 2; repeated Seq code = 3; int32 line = 4; uint64 flags = 5; }
message Seq    { repeated Code code = 1; }
message Arg    { oneof kind { Constant constant = 1; uint32 name = 2; uint32 proc = 3; int64 int = 4; Pattern pattern = 5; FieldDecl field = 6; } }
```

The IR depends on no value of a run: a literal is a `Constant`, and
`cameo/ir.proto` imports nothing. `cameo/value.proto` imports it, for the
value that refers to code, a Proc:

```proto
message Closure { string unit = 1; uint32 proc = 2; Unit code = 3; Binding binding = 4; bool strict = 5; string self_name = 6; string symbol = 7; Value recv = 8; }
message Binding { repeated Local locals = 1; Value self = 2; string self_class = 3; Method method = 4; repeated string lexical = 5; string def_target = 6; string file = 7; repeated Value args = 8; Map kw = 9; Value block = 10; }
```

`eval/closure.go` turns a Proc into a `Closure` and back, through
`protogen.ProcCodec`.

- **Names are indices** into the unit's table, as atoms are in Erlang's
  distribution header.
- **A unit's digest** is a hash of its wire form. A closure names its unit
  by it and its proc by index, as an Erlang fun names its module, index and
  uniq. The first closure of a message that refers to a unit carries the
  unit in `code`, when the encoder carries units at all; the reader keeps
  it for the closures that follow, and checks that it hashes to the digest.
  A closure whose unit is neither in the message nor in the program is
  refused.
- **The locals of a binding are the ones the code reads**, found by walking
  the proc and the blocks written in it, not all that were in sight: a
  local the code never names does not travel, and cannot stop the proc
  from travelling. A local that holds a class travels as the class's name.
- **`self_name`** is the local that holds the closure itself: a lambda that
  calls itself by the name it is assigned to. The decoder binds it, so the
  message holds no cycle.
- **The frame travels by name**: self by value, or as a class's name, or
  as nothing for the top-level self; the method the proc was written in as
  its class and name; the lexical classes by name. The arguments and the
  block of that method's call travel only when the code has a bare `super`
  or a `yield`. No call is running the frame of a decoded proc, so its
  `return` raises `LocalJumpError`, as Ruby's does for a proc whose method
  returned.
- **A proc a builtin made does not travel**: it is a Go function. A proc
  made from a symbol does, as the symbol.
- **A symbol in a binding reads back as a String**, as a symbol does
  wherever a value crosses the envelope ([cameo.md](cameo.md#symbols)). A
  proc that compares a captured value with a symbol compares differently
  after it travelled. Whether the envelope should carry symbols, now that
  it carries what a running program holds, is an open question.
- **Every instruction carries its line**, for error messages and the
  debugger.
- **Locals are addressed by name.** A binding is then names and values with
  nothing to translate, and irb and the debugger evaluate a line in it.

`cameo ir script.cameo` prints the listing; the tests of the compiler compare
listings.

## Running it

Stack A runs the IR with a recursive evaluator, so a run still pauses between
top-level statements, but its dump carries procs, classes and methods.

**The IR is what runs.** A program is compiled to one unit before its first
statement runs (`ir.Compile`): the script, each library written in cameo
that it requires, each line of a console. `eval/vm.go` runs the unit: a
machine per activation, with a value stack, the scope and the frame. Proc 0
of a unit is its top level, whose statements the run takes one at a time, so
that it can pause between two of them. A method's body is a proc
(`object.Method.Body` holds an `*irProc`), and so is a block's
(`eval.Proc.IR`). The AST is the compiler's input and nothing else reads it
at run time; `cameo build` compiles from it too, apart from the IR.

The tree walker and the closure compiler it replaced are gone. While the
IR was built in slices, both evaluators ran every test, and ruby/spec's
language and core examples had the same status on each, 3,938 rows without
a difference, before the tree walker was removed.

Stack B replaces the recursion with a stack of activations per interpreter,
which the next section describes. Two parts of it are built. Inside one
activation the lists of an instruction run on cursors (`eval/cursor.go`),
and a completion unwinds them. And an interpreter has one stack of
activations and one loop (`eval/stack.go`): a `SEND` or a bare name whose
method a script defined, and a `YIELD` to a block a script wrote, push an
activation and go back to the loop. Every other way into a method or a
block still starts a loop of its own, nested in the one that runs: a
builtin calling its block, `super`, an operator a class defines, a
parameter's default, `Proc#call`, the expression inside a pattern.

A script's recursion no longer rides on Go's stack, which ended the
process at about a million calls: a call past 200,000 activations raises
`SystemStackError`.

## The activation stack

Stack A left one thing on the Go stack: where a run is. `machine.exec` calls
itself for the lists inside an instruction, `Interp.invoke` calls
`runBody` for a method, a builtin calls `callBlock` for its block, and a
`rescue`, a `break` and a `return` travel as Go errors through all of
them. Stack B moves that state into data, one piece at a time, with the run
able to pause wherever the pieces built so far cover it.

### An activation

An **activation** is one proc that is running: a method call, a block call,
a class body, the top level.

| part | is |
|---|---|
| the proc | a unit and a proc index, as a method and a closure name their code |
| the position | a **cursor** per list the activation is inside, outermost first |
| the value stack | the operands of the expression in flight |
| the scope | the local variables, `eval.Env` |
| the frame | self, the method, the block, the lexical classes: `eval.Frame`, as today |
| the return | what the caller does with the result |

A cursor is a list of instructions and the index of the next one. The
first cursor is the proc's own list. An instruction that holds lists, `IF`,
`WHILE`, `BEGIN`, `CASE`, `INTERP`, does not call the evaluator for them:
it pushes a cursor for the list it enters and returns. When a list ends the
evaluator pops its cursor and asks the instruction that owns it what comes
next, with the **phase** the cursor was pushed in: `WHILE` after its
condition pops the value and enters the body or leaves, after its body
enters the condition again. So a cursor is three numbers, the index of the
next instruction, the list of its owner it runs, and the phase, and the
position of an activation is a path of them. Nothing else of an instruction
in flight is hidden: what `CASE` compares against and what `INTERP` has
built so far are on the value stack.

`BEGIN` keeps two things on its cursor beside the numbers: the exception a
`rescue` clause is handling, which `raise` without arguments and `cause`
read, and, while an `ensure` clause runs, what the clause interrupted — a
value, an exception, a `break` — which goes on when the clause ends.

An interpreter has one stack of activations: the script's interpreter, and
each worker an `async` call runs in.

### Calls, returns and unwinding

A `SEND` whose method a script defined pushes an activation and returns to
the loop; so do `YIELD` and `Proc#call` for a block a script wrote. The
parameters are bound before the first instruction, and a default that is
code runs as a list of the new activation, with a phase per parameter.
When the proc's list ends, the activation is popped and its value handed to
the return of the activation below: pushed on its value stack, usually, and
for the calls that do more, a step of the instruction that called — `SEND`
rebinding the receiver's variable for `list << x`, `CLASS` binding the
class once its body ran.

What leaves a list early is a **completion**: an exception, `break`,
`next`, `redo`, `retry`, `return`, `throw`. The evaluator unwinds for it,
cursor by cursor and activation by activation, instead of returning a Go
error through its callers:

- a `WHILE` cursor takes `break`, `next` and `redo`
- a `BEGIN` cursor in its body takes an exception one of its clauses
  rescues, a `BEGIN` cursor in a clause takes `retry`, and one with an
  `ensure` clause runs it, keeping the completion
- a block's activation takes `next`; the activation that passed the block
  takes `break`; the activation of the method the block was written in
  takes `return`
- `catch` takes the `throw` of its tag

An activation that is popped on the way marks its frame as ended, as a
return does.

### Builtins, and where a run can pause

A builtin is a Go function, and one that calls a block or a method calls
back into the evaluator: `List#each` its block, `puts` a `to_s`, `sort` a
`<=>`. Today that call runs the block to its end on the Go stack. It keeps
working: the evaluator pushes the activation and runs its loop, nested,
until that activation returns. But a run cannot pause inside a nested
loop, since the builtin's own state, how far `each` has come, is in Go
variables.

So the rule for a pause is: **a run pauses before an instruction when no
nested loop is running.** `^C` sets the flag as before; the loop reads it
before each instruction, and pauses or carries on to the next instruction
that qualifies. A script that spends its time in its own methods and
`while` loops pauses at once. One inside `list.each { … }` pauses when
`each` returns, until `each` is a step function.

A **step function** is a builtin written so that its state is data:

```go
// A Stepper runs a builtin up to its next call into cameo code. state is
// what the previous step kept, nil on the first; result is what the
// call it asked for returned.
type Stepper func(ctx Context, call *Call, state []Value, result Value) (Step, error)

// A Step is what a stepper wants next: Yield calls the block with Args
// and comes back with its result and State; Done ends the builtin with
// Value.
type Step struct {
	Done  bool
	Value Value
	Args  []Value
	State []Value
}
```

`List#each` keeps one number, the index of the next element. The evaluator
gives a step function an activation of its own, without code: the builtin's
class and name, the receiver, the arguments, the block, and the state. It
calls the step, pushes the block's activation, and calls the step again
with the result. No nested loop runs, so a run pauses inside the block,
and the dump holds how far the builtin came. A `break` out of the block
unwinds through the builtin's activation; a builtin that must clean up,
`File.open` closing its file, says so in its step and is called once more
with the completion.

Builtins become step functions in groups, the ones a script spends its time
in first: `Integer#times` and `loop`, then `each`, `map` and the rest of
List, Hash, Range and Set, then Enumerable over a script's own `each`, and
so on. Each group widens where a run pauses and changes nothing else, and a
builtin that never becomes one, because it calls back for an instant, only
ever delays a pause. An Enumerator is the same idea turned around: `next`
runs the stepper of the method it enumerates one step.

A method `cameo build` compiled is Go code too, and a nested loop when it
calls back. It is pure, so at a pause it leaves its call to the
interpreter (`eval.ErrDeopt`), which runs the body again from its start as
an activation.

### The dump

A dump of a run that paused inside a statement adds the stacks to what
step 16 carries:

```proto
message Stack {
  repeated Activation activations = 1;   // outermost first
  // what the interpreter is for: the script, or the call async started
  int64 promise = 2;
}

message Activation {
  string unit = 1;             // the proc, as in a Closure
  uint32 proc = 2;
  repeated Cursor cursors = 3;
  repeated Value stack = 4;
  uint32 scope = 5;            // an entry of Dump.scopes
  uint32 frame = 6;            // an entry of Dump.frames
  // for a step function instead of a proc: its class and name, the call
  // and the state
  Builtin builtin = 7;
}

message Cursor {
  uint32 next = 1;             // index of the next instruction
  uint32 list = 2;             // which list of the owning instruction
  uint32 phase = 3;
  Value rescuing = 4;          // BEGIN: the exception a clause handles
  Completion pending = 5;      // BEGIN: what its ensure clause interrupted
}
```

Scopes and frames are tables of the dump, referred to by index, because
they are shared: a block's activation and the activation of the method it
was written in have one frame, which is how the block's `return` finds the
method and its `yield` the method's block; a `for` body shares the scope
of the code around it. A closure that is a value in such a dump names the
frame it was written in by its index while that frame's call is running,
so that its `return` still works after the resume, and carries its binding
as a closure does today once the call ended. Values need no table: they
never change, so a copy is the value. An instance that `initialize` is
still filling is the exception, and is in the frame.

The pause still waits for nothing it can stop instead. Each worker stops
at its next instruction that qualifies and its stack is dumped under the
promise it will settle; a call `async` queued and no worker took yet is
dumped as the call. A promise the host is to settle stays pending in the
dump, and the host settles it after the resume, by its id.

A resumed run rebuilds the stacks: every activation finds its proc by
unit and index, its cursors by walking the path, and a step function by
its class and name. A cameo that no longer has a builtin a dump is inside
refuses the dump.

### What stays on the Go stack

The host calling into a program (`Program.Call`) is a nested loop of the
host's making, and a run does not pause inside it. Neither does it inside
the debugger's prompt or a builtin that is no step function. These are the
places a pause is late; none makes a dump wrong.

## The stack of pull requests

Branches are `ir/NN-<topic>`, each based on the one before, the first on
`main`. Every pull request leaves `make check` green. A branch's number
counts pull requests, so it runs ahead of the step numbers below where a
step took more than one.

**Stack A: an IR, and procs, methods and classes that serialise**

1. doc: this document.
2. eval: the tree walker evaluates every node but calls.
3. eval: the tree walker evaluates calls; `compile.go` goes.
4. build: `make proto`, the pinned tools and the CI check; `cameo.Value`
   moves to `src/cameopb/cameo/value.proto` and generated code.
5. protogen: the dump moves to a `.proto` file and generated code.
6. ir: `ir.proto`, the instruction set, and the listing printer.
7. ir: compiles and runs literals, variables, calls, blocks and control
   flow; `cameo ir`.
8. ir: compiles and runs exceptions, `case`, patterns, multiple assignment,
   ranges, maps and strings.
9. ir: compiles and runs definitions, `super`, `with`, `async` and `await`.
10. eval: every program runs on the IR; the tree walker goes. The debugger
    and irb move over. `cameo build` stays on the AST.
11. eval: a frame knows when its call ended, and a `return` from a proc
    that outlived it raises `LocalJumpError`. A frame keeps pointing at its
    method and classes; the closure of step 12 names them when it is
    encoded.
12. protogen: `cameo.Value` carries a closure, with its binding and a table
    of units.
13. async: a Proc crosses to a worker.
14. cameo: `Program.Encode` and `Decode` carry a Proc.
15. pause: a dump carries procs and the blocks `at_exit` registered.
16. pause: a dump carries classes, modules, constants and methods; resume
    runs no definition again. The dump has an IR version.
17. protogen: a Hash with a default proc travels.

In 7 to 9 a method or block that uses an instruction not built yet stays on
the tree walker, whole, and the examples run on both evaluators with their
output compared.

Step 16 took a second pull request, for the class of an instance that was
made before its class was reopened.

**Stack B: a run pauses at any instruction**
