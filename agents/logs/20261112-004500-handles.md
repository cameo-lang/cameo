## Objective
Step 27 of `doc/design/ir.md`: a library says how one of its values that
change goes through a dump, and a StringIO does.

## Progress
- [x] `object.StateHook` on a class: `Save` and `Restore`
- [x] `cameo.Value.handle`, written and read by a dump alone;
      `Encoder.WithHandles`, `Decoder.WithHandles`
- [x] `Dump.handles`: each handle once; `eval/handles.go` collects them
      while the dump is written and makes them all in `Resume`
- [x] StringIO saves its string, position, line number and how it is
      open
- [x] Tests: a StringIO held by two variables, a list, a Proc and the
      block of a `loop`, through five pauses; a handle without a hook is
      named

## Obstacles
- **Issue:** A handle is shared: `same = io` and `io` are one StringIO,
  and reading from one moves the other. A value in the envelope is a
  copy.
  **Resolution:** The dump keeps a handle in a table and writes a
  reference wherever a value is that handle. Resume makes the table
  before the values, and every decoder of the resumed run, a worker's
  too, reads references from it.
- **Issue:** Two tests used a StringIO as what a dump cannot hold.
  **Resolution:** They hold an Enumerator now.

## Outcome
A script that reads or writes a StringIO pauses and resumes with it. A
File, a Logger and the other handles need their libraries to give them
the hook; what a library keeps on a class, Singleton's instance, is not
covered by this hook.
