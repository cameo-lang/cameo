# Task: super and a class's operators as activations

**Started:** 2026-11-11 22:50:00
**Ended:** 2026-11-11 23:05:00
**Strategy:** Feature (TDD)
**Status:** Completed
**Complexity:** Simple
**Used Models:** Fable 5.2
**Token usage (Estimated):** 150k input, 9k output

## Objective
A method that `super` calls, and an operator a class defines, ran through
a call of the evaluator from inside the instruction, so in a loop of its
own.

## Progress
- [x] `callSuper` split into `superMethod` and `callSuperTo`; `SUPER`
      pushes the activation of a method a script defined
- [x] An operator send that the fast path does not answer goes through
      `machine.call`, as any `SEND` does
- [x] `Frame.building_of`: an `initialize` that a `super` in another
      `initialize` called fills the same instance after a resume
- [x] Tests: pauses inside a method under `super`, an `initialize` under
      `super`, a class method under `super`, and `+`, `==`, `<=>`, `-@`
      and `[]` of a class

## Obstacles
- **Issue:** With `super` an activation, a run pauses with two frames
  that fill one instance: a subclass's `initialize` and the one its
  `super` called. The dump of the step before held the instance in each
  frame that fills it, which would make two after the resume.
  **Resolution:** The first frame holds it, and the other names that
  frame in `building_of`.

## Outcome
The calls an instruction makes into a script's own methods are all
activations now. What is left on the Go stack is what a builtin calls:
its block where it is no stepper, and `to_s`, `==`, `<=>` or `each` of a
script's object.
