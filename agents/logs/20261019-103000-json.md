## Objective
`require "json"`, `JSON.parse`, `generate`, `dump`, `pretty_generate`,
`to_json` on every builtin value and `JSON::ParserError`, matching Ruby 3.4
(json 2.9.1) byte for byte, and a documented rule for cameo instances.

## Obstacles
- **Issue:** ParserError messages quote the input from a place that depends on the construct: an array reports the element or separator, an object reports its own start, a NaN or a broken surrogate pair reports itself.
  **Resolution:** The parser returns a failure for strings, numbers, literals and objects, which the caller reports at the value's start, and raises in place for the rest; every probe input agrees with Ruby.
- **Issue:** cameo's `Float#to_s` printed 1e15 as `1000000000000000.0`; Ruby prints `1.0e+15`.
  **Resolution:** Moved the threshold in `object.FormatFloat` to 1e15 and checked 21 floats against Ruby.
- **Issue:** The checker rejected `JSON.parse!` as a bang method and `JSON.load` as Kernel#load.
  **Resolution:** An explicit list of library functions those checks skip.
- **Issue:** doc/gh_pages/ruby.html showed `require "json"` failing, which its site test runs.
  **Resolution:** The sample requires `yaml` instead; three lines changed, since that page is being rewritten elsewhere.

## Outcome
JSON matches Ruby 3.4's output and error messages on every probe, except
that an instance of a cameo class is an object of its fields, a class's own
`to_json` receives a Hash rather than a `JSON::State`, and a binary String
gets no deprecation warning.

## Insights
Ragel-generated parsers report errors at the start of the machine that
failed, so the position differs per construct; probing many malformed
inputs was the only way to pin it down.
