## Objective
Step 20 of `doc/design/ir.md`: a call of a method or a block a script
wrote is an activation on the interpreter's stack, run by one loop, where
it was a call of the evaluator on the Go stack.

## Progress
- [x] `eval/stack.go`: `Interp.acts`, `start`, `run`, `pushAct`, `leave`
- [x] `invoke` and `callBlock` split into making the activation
      (`methodAct`, `blockAct`) and what happens when it ends (`leave`)
- [x] `dispatch` split into `lookup` and `dispatchTo`, so that an
      instruction can decide between pushing and calling
- [x] `SEND`, a bare name and `YIELD` push an activation
- [x] A call past `maxDepth` activations raises `SystemStackError`
- [x] Tests: the number of activations and loops at four places; depth;
      every completion that crosses a call
- [x] `make check`; conformance and ruby/spec statuses unchanged

## Obstacles
- **Issue:** The expression inside a pattern runs to its end inside the
  instruction that matches the pattern. A call in it that pushed an
  activation and returned would be run after the match went on.
  **Resolution:** `machine.inGo` counts such lists; a call made while it
  is not zero starts a loop of its own, as a builtin's does.
- **Issue:** `git stash` to build the commit below for a comparison left
  the new files in place, and the build failed. Known from before; I
  used it again.
  **Resolution:** Compared against the binaries kept from each step.
- **Issue:** The binary kept as the baseline was built before a `return`
  from a proc whose method ended raised `LocalJumpError`, so one script
  differed on it.
  **Resolution:** Compared against the binary of the step below.

## Outcome
`fib`, a method that yields and a block that returns out of two methods
run in one loop. `[1].each { … }` and the other ways into a block from Go
start a nested loop, which is what step 21 holds a pause off for and what
the step functions of step 22 on take away. A small benchmark of calls
and loops runs about a third slower than on the evaluator of stack A.
