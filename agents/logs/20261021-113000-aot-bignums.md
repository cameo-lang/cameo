## Objective
Step three of doc/design/aot.md: an Integer that outgrows 64 bits stays in
Go instead of sending the call back to the interpreter, measured on
tests/performance/02-bignums.

## Progress
- [x] Every compiled method gets a twin on *big.Int, written by the same generator in a second mode
- [x] The entry runs int64 first and the twin on overflow, or at once for an argument beyond 64 bits
- [x] Tests: the generator writes the twin; arith's power(2, 64) and floor_div(2**64, 2**60) answer in Go; a zero divisor and a Float still leave
- [x] Examples regenerated; conformance 61 of 61 same; make check
- [x] fact: compiled 0.437 s to 0.208 s, the interpreter's 0.426 s halved

## Obstacles
- **Issue:** The design listed "big.Int in place", a checked operation that grows mid-method. The method's int64 locals cannot hold a big.Int, so the whole call has to run again in another form.
  **Resolution:** A twin of the method on *big.Int, which runs the call from the start. Starting over is safe since compiled methods are pure, and cheap since the overflow is found at the first big result.

## Outcome
Compiled methods compute past 64 bits in Go. Division by zero and
non-Integer arguments are the deopts left.

## Insights
The twin allocates a big.Int per operation and literal; the literals are
hoisted to package-level constants that no operation changes.
